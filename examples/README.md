# 星舟商城虚构知识工作区

本目录是一套人工编写的售后运营演练资料。商城、产品、订单、活动、流程和价格均为虚构，不代表真实商家的服务承诺、法律或税务规则、产品认证、交易结果或模型效果。

## 第一次载入与查看结果

这套输入是仓库中的16份虚构Markdown原文、manifest和人工Wiki定义，不需要你先填写真实客户数据。

从仓库根目录执行：

```powershell
python -B -m zhiwiki --config config.example.json seed
python -B -m zhiwiki --config config.example.json serve --port 8875
```

打开http://127.0.0.1:8875，提问、展开原文引用，再查看sample前缀的人工Wiki。输出是本地数据库中的文档/片段/示例Wiki及页面回答，不会自动往examples目录写一份新Markdown。

要导出文件，先列出实际Wiki ID，再按主README的wiki export命令指定输出路径。再次seed保持既定幂等规则，不会替你覆盖已编辑的用户页面。数据均为虚构，offline摘录不等于模型效果评测。

## 内容与导入

`manifest.json` 是唯一的资料导入清单，固定列出 16 份 Markdown 原文及其标题、分类、更新时间、来源键和简介。`README.md`、评测题和 Wiki 定义不进入原文知识库。只有用户显式执行样例载入动作时才导入；包导入和服务启动不自动载入这些资料。

保留的四份初始资料为 `refund-2025`、`refund-2026`、`shipping`、`warranty`。它们的原文和来源键保持不变。其余资料覆盖产品规格、订单时间线、质检、逆向物流、优惠分摊、会员、支付状态、发票、包装、客服分流和秋季活动。

订单、质检、逆向物流和优惠退款四份手册均超过 2,000 个中文字符，正文有层级标题、条件边界和跨文档关系，用于体验真实的多个分块与原文定位。重复规则用于保留岗位上下文，不意味着不同资料已经被模型自动判定一致。

## Wiki 示例

`wiki_samples.json` 包含四个 `sample-` 前缀页面，主题分别为政策日期、质量换货、组合退款和设备支持。结论由人工编写，标记 `mode=sample`；不是模型生成结果。载入时先逐字核对其中的来源摘句确实存在于当前原文分块，再建立可追溯引用并发布这组明确的示例页面。

再次载入时，同内容、同来源且仍有效的示例页面保持幂等。已有同名用户页面或被编辑过的页面不会被覆盖或自动发布。失效的旧示例页需要正常复核，不会因点击载入就被悄悄重建成可信页面。

## 两种版本不能混淆

业务上的 2025 版政策和 2026 版政策是两个不同 `source_key`，用于按订单创建日期选择历史业务规则。因此首次导入时，它们在数据库中都可以是文档 `version=1`。

要演示知识失效，应更新同一个来源键的正文，使数据库生成新修订。引用该来源旧分块的 Wiki 随后失效。仅增加另一份新名字文档，不代表系统知道它替代旧来源。

## 评测边界

`evaluation.json` 为 24 道虚构问题，保留原 12 题并加入产品、质检、物流、活动、会员与对账场景。每题列出期望原文来源和人工答案核对点。期望来源覆盖不等于答案正确率；长文加入后检索候选竞争也更明显，不应把样例结果包装为真实业务收益或模型推理能力。
