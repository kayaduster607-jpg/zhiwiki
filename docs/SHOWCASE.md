# 三分钟演示、简历表述与面试追问

知证面向需要反复核对政策、产品与售后资料的知识维护者。核心问题是：回答需要回到依据，整理后的知识又会随着依据更新而失效。项目用有界 Agent 查询、原文版本、带引用的 Wiki 和显式审核处理这条链路。

本文基于现有代码设计可复现演示，不把演示脚本当成已经执行的验收。实际操作记录与最终数字见 [ACCEPTANCE](ACCEPTANCE.md)。本轮跳过真实模型，演示保持 `offline`，工具轨迹可以查看，模型调用为 0；它展示工程闭环，真实模型自主取证与答案质量仍待单独验证。

## 1. 演示前准备

使用已有可运行服务的解释器，在独立目录载入虚构样例：

```powershell
python -B -m zhiwiki doctor
python -B -m zhiwiki --provider offline --data-dir data-showcase seed
python -B -m zhiwiki --provider offline --data-dir data-showcase serve --port 8767
```

打开 `http://127.0.0.1:8767`。`data-showcase` 是专用演示工作区；重复 seed 不覆盖已有手工修订。首次载入应有 16 份原文、28 个 fixed 片段、4 篇人工示例 Wiki。资料和结论来自仓库明确清单，属于虚构案例，不代表真实企业政策，也不是模型生成质量样本。

提前在该工作区用“添加或更新资料”的文本表单创建一份短资料：标题“演示售后规则”，来源标识 `showcase-policy`，正文“普通商品签收后七天内可以申请退货，商品应保持完好。”然后只选这份资料生成 `showcase-returns` 草稿，核对并发布。后续演示只修改这个专用来源，避免影响已载入样例的评测口径。

将下面四项放在可随时打开的位置：一条原文详情、该 Wiki 详情、[架构说明](ARCHITECTURE.md)、[检索基准](RETRIEVAL.md)。演示时直接操作关键流程，不需要现场配置模型或等待长文编译。

## 2. 三分钟操作与讲述

| 时间 | 操作 | 建议讲述 | 观众看到的证据 |
|---|---|---|---|
| 0:00–0:25 | 工作台概览，打开原文与 Wiki 数量 | “知识问答有两件事：当下找到依据，以及维护已经整理过的结论。原文、Wiki 和查询记录分别保存。” | 虚构样例标签、16 原文/28 片段/4 示例页；准备的专用资料另计 |

| 0:55–1:35 | 打开 `showcase-returns` → 人工修订；将摘录改写为等义结论，保留并核对原文引用；备注填写“核对适用条件”；保存 | “保存产生下一版 manual 草稿。旧页保留，发布需要另点一次；两个编辑者拿着同一旧版本保存时，后提交者会收到版本冲突。” | 新 ID/版本、draft 状态、维护备注与原文引用分开；原发布版仍可用 |
| 1:35–2:10 | 发布新稿；文本表单使用相同 `showcase-policy` 将“七天”改成“十五天” | “稳定来源键表示同一份资料。更新原文与 Wiki 失效在同一事务里提交，旧知识不会继续充当有效发布页。” | 原文下一版本、新片段 ID、Wiki stale；旧引用仍能读但 active=false |

| 2:40–3:00 | 打开架构与切分，比较 fixed/structure 预览，展示检索文档的冷/暖路径表 | “900/120 是字符基线，结构策略仍是预览实验。性能优化复用词频并用数据库 epoch 感知变更，最终回答仍重新查证来源。” | 实际 offset/边界原因；明确区分参数实验、本地基准与生产指标 |

如果现场时间紧，来源更新后停在 stale 页面即可，修复过程留给追问。不要把离线步骤读成模型规划，也不要把本地缓存耗时读成模型回答时延。

### 上传流程的补充演示

准备两个同名 TXT 文件时，新建上传分别生成独立来源；可填写不同显示标题。要产生下一版，选择“更新已有资料 · 创建新版本”，核对标题、版本、ID 末 6 位和前 400 字预览，再提交。新建与更新的意图显式分开，避免文件名碰撞隐式改动原文；更新请求带目标 ID 与预期版本，服务器在事务内再次检查。

### 并发冲突的补充演示

用两个浏览器页面打开同一最新 Wiki，分别进入人工修订。A 保存后，B 继续提交旧 `expected_version` 应得到 409，并保留编辑文字供比较。这里没有跨用户登录或自动三方合并；两个页面只用来复现旧编辑基础与新版本的竞争。自动测试还覆盖来源更新与修订同时执行、插入后故障回滚，见 [WIKI_REVISIONS](WIKI_REVISIONS.md)。

## 3. 可以据实际职责裁剪的简历表述

项目描述：**面向企业知识维护的 Agentic RAG + Wiki 工作台**，基于 Python、FastAPI 与 SQLite，实现可追溯问答、原文版本管理、带来源的知识修订及更新失效闭环，提供原生浏览器工作台和 CLI。

- **设计有界检索执行器**：接入 OpenAI 兼容工具调用协议，提供文档搜索、Wiki 搜索、证据读取 3 个只读工具，控制轮次、工具与上下文预算，并在最终输出前复查本次取得的原文引用；通过脚本模型与 Mock HTTP 验证控制流和失败边界。
- **实现知识版本与审核流程**：以 SQLite 事务维护原文、片段和 Wiki 依赖，支持人工逐条修订、显式发布、原文更新失效与历史导出；用 `expected_version` 防止旧编辑提交覆盖新修订，维护备注与可检索证据分离。
- **优化词法检索的重复读取与分词**：实现批量候选查询和 epoch 感知的 BM25 内存缓存；在 64 份合成资料、256 片段的本地微基准中，单次搜索 SELECT 从旧路径 257 条降为冷路径 4 条、暖路径 1 条，三条路径逐查询核对结果一致。

第三条的数字来自 [原始微基准](../reports/retrieval-benchmark.json)，有固定小型合成语料、每路径 12 样本和仪器开销边界。不要改成生产 QPS、用户增长或答案正确率。模型适配已经实现与真实模型效果已验证也要分开表达；当前不能填写 Agent 提升百分比或真实模型通过率。

## 5. 面试追问与回答

### 为什么做 Agentic RAG + Wiki，而不是只换一个检索框架？

我的目标是处理两种问题：一次查询可能需要分步取证，已经整理的结论又需要持续维护。Agent 的职责在一次 run 内，Wiki 的职责跨越多次查询；二者共用证据结构，但写权限分开。模型工具只有搜索和读取，人工修订与发布通过独立接口执行。

固定 RAG 仍作为对照，按原问题搜索原文 top 5 和 Wiki top 3，再生成一次回答；Agent 可根据工具结果继续取证。当前用显式有限循环，使预算、工具白名单、终止状态和引用检查集中可见。LangGraph 的图节点、持久中断等能力适合更复杂编排；现阶段没有这些需求，也没有引入其运行依赖。Wiki 本身不是 GraphRAG：没有实体社区抽取，价值来自来源依赖与审核生命周期。

**进一步追问：怎么证明 Agent 有收益？** 当前离线两策略同为确定性摘录，不能证明自主取证收益。应先联调真实服务，再冻结语料、模型、提示和预算，在未参与调参的问题上比较答案正确、引用支持、跨来源覆盖、拒答、成本和时延。脚本模型证明“循环允许继续检索”，真实评测才能证明“模型实际选对了下一步”。

### 为什么选 SQLite，原文变化时如何避免半更新？

当前是单机工作区，版本记录、片段和 Wiki 依赖可以放在同一个关系库里。更新使用 `BEGIN IMMEDIATE`，先核对当前来源，然后同时撤下旧原文、标记相关 Wiki、插入新原文和片段。失败整笔回滚，模型网络调用期间不持有写事务。WAL 允许读者使用已有快照，但不能让多个写事务同时提交。

Markdown 是导出物，数据库是事实源，所以没有数据库提交成功而文件镜像半更新的双写协议。PostgreSQL 更适合多实例服务和较大写竞争，文件库更易人工浏览；本项目选择 SQLite 是因为事务关系清楚、已有环境可运行、备份范围明确，而不是声称它在所有规模下最优。

**进一步追问：重复请求怎么办？** 标题和内容哈希未变的稳定来源键导入返回 unchanged。人工修订则要求 base 仍是最新版本，第一次成功后重放会冲突，避免生成多个相同新稿；它不是幂等响应缓存。客户端遇到未知网络结果要先读最新状态再决定，不盲目重试。浏览器新增上传表示创建独立来源，重复新增会产生不同来源，这与更新是两种意图。

### 既然用了数据库事务，为什么人工修订还要 expected_version？

事务保证一组读写原子完成，却不知道用户是基于哪版页面编辑。若 A、B 都从 v3 开始，A 保存 v4 后，B 的事务仍可能正常运行；没有编辑基础检查时，B 会把旧意图直接写成 v5。因此保存必须同时验证 base ID、预期版本和“仍是同 slug 最新修订”，然后在同一事务检查原文并创建新草稿。

这里采用乐观并发控制：用户编辑过程中不持有数据库锁，只有保存时短暂检查。长时间锁住 Wiki 可以阻止别人编辑，但容易受浏览器关闭、超时和离线影响；自动合并文本又需要按 claim 和引用定义冲突规则。当前拒绝冲突，让人比较内容，维护成本和行为更清楚。

**进一步追问：来源和编辑同时变了呢？** 写事务会排序。来源更新先提交，保存就看见失效引用并拒绝；修订先提交，来源更新会把新稿一并标记 stale。保存不会覆盖 base，也不会自动发布，发布时再核对来源。因此可以修订 stale 页面，但新提交必须替换全部失效引用。

### 缓存会不会重新把失效 Wiki 送回模型？

缓存按 SQLite epoch 管理，每个存储实例独立保留内存索引。相关表的触发器和业务写入同事务推进 epoch；检索在同一个读取事务里取得 epoch 与候选，所以不会把旧代次和新正文错误配对。热路径复用词频与倒排集合，下一次查询发现变化就重建整份当前语料。

一次查询仍可能返回开始读取时的合法快照。最终答案因此必须再次直接读取原文/Wiki及其底层引用，拒绝已失效的证据。缓存优化读取成本，不能取代来源时点检查。`RLock` 防止同实例并发冷构建，排名在锁外，返回副本防止调用者污染缓存；多进程各有自己的内存，依赖数据库 epoch 协调失效。

**进一步追问：为什么不用 SQLite data_version 或每次重建？** `PRAGMA data_version` 只适合比较同一连接不同时间的结果，本项目按操作新建连接，不能把它当全局代次。每次重建确实容易保持读快照，但重复读正文和分词；当前本地基准显示暖缓存减少这些成本，冷路径仍需全量分词。若写入频繁、语料很大，下一步应测量内存和重建开销，再选择增量或持久索引，而不是外推这次微基准。

### 900/120 从哪里来，结构切分已经改善检索了吗？

900 与 120 是字符窗口和重叠的起始基线，不是官方最佳值。默认 fixed 在窗口后半部分寻找靠后的换行或中文句号，保存原文精确 offset；字符单位可以用标准库精确验证，不依赖供应商 tokenizer，但不能保证 token 上限和完整语义。

structure 根据官方原则做本地预览：先按 ATX 标题划节，围栏内不识别标题，再在节内按段落、句末与字符上限处理。它不跨节重叠，围栏可能使实际重叠减少。现有入库保持 fixed，避免在没有策略版本和依赖迁移规则时改变片段身份。性质测试证明切片完整、偏移正确，尚未证明结构策略的业务检索收益。

**进一步追问：改用 Parent-Child 或向量检索呢？** Parent-Child 将召回粒度与阅读粒度分开，需要父子 ID、去重和额外上下文预算；向量检索处理同义表达，需要真实嵌入模型、索引更新和供应商成本。当前统一 evidence 协议给这些扩展设定引用规则，但没有对应 backend。应从漏召回和跨边界失败样本选择实验，不能靠更换名称判断效果。

### 怎么保证模型不乱编？超时后是否自动降级？

当前能保证明确的结构边界：最终 JSON 合法、引用在本次已取得集合中、返回前来源仍有效；不能自动证明一条结论由原文语义蕴含。人工发布、逐条引用与独立人工评分就是为后一个问题保留的环节。维护备注没有来源，所以只存在详情和历史导出，不能混入知识检索正文。

每轮预算包含完整 messages 和工具定义；历史工具结果再次发送要再次计输入成本。未知或非法工具也计调用次数。供应商 usage 缺失或矛盾时采用保守估算并标记 unknown，不能用缺失值当零费用。HTTP 客户端限制响应体大小并逐块检查时间，但同步阻塞 I/O 不能保证操作系统级硬截止；执行器在步骤与最终输出边界复查总时限。

**进一步追问：失败后为什么不悄悄回离线？** 真实模式失败返回 provider_error 或明确预算/格式状态，避免用户把摘录误当模型回答。离线模式是显式选择的产品能力，不是掩盖故障的无声降级。SSE 只传公开步骤和最终结果；客户端断开会阻止后续步骤，已派发同步请求无法撤回。排查时按 run 的 stop_reason、公开工具参数、调用次数与引用状态定位，不记录供应商私有推理内容。

### 项目用了哪些设计模式，它们解决什么？

`create_app` 使用应用工厂组织依赖，测试可以注入临时存储。provider 通过相同 complete 接口注入真实适配器或脚本替身，是策略式依赖替换；没有为了模式名称额外堆叠继承层。`on_event` 回调把执行过程通知给 CLI 或 SSE，是观察者式通知。Wiki 状态通过事务规则转换，属于显式状态机，但代码没有独立的 State 类层次。

这些选择让核心循环不用关心浏览器连接，也让 API 不复制业务规则。代价是接口契约必须稳定：事件取消异常不能被吞掉，替身必须复现真实协议的必要字段，新增模型服务要继续满足预算和错误脱敏。若未来支持可持久化任务、多人审核或多检索器，先扩展契约和一致性测试，再考虑框架；当前无需把每个普通函数包装成设计模式。

## 6. 讲述前的事实检查
