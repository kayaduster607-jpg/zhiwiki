# 检索、中文词项与快照缓存

本文对应第三轮实现，核验日期为 2026-09-09。项目继续使用标准库实现的词法 BM25；没有安装 Elasticsearch、Lucene、中文分词包或向量模型。官方资料提供设计依据，不代表本项目具有这些系统的吞吐量或效果。

## 1. 中文漏召回的原因与修复

旧版把包含任意中文功能字的二元词项全部排除。例如“和田”的“和”、“也门”的“也”、“与门”的“与”、“异或”的“或”都触发排除，导致精确词项也无法成为召回依据。

新版保留英文完整词与连续汉字的单字、相邻二元词项。查询先移除“是什么”“的含义”等完整问句结构，再生成内容锚词；不会单独删除内容词首尾的功能字，以免“目的”“求是”等词被截坏。只有两个字**全都**属于功能字集合的二元词项才被视作通用连接词；不会因为复合词中一个字恰好是功能字而删除整个词项。实现没有四个示例词的特殊名单。

召回入口仍要求完整英文内容词或中文二元内容词匹配。中文单字参与排序，但多字查询不能只靠共享一个字召回；明确输入一个非功能单字仍可查找该字。纯问句、问词和纯功能字不能独立成为锚点。

Elastic 官方 CJK bigram filter 支持二元词项，并允许同时输出单字；stop filter 则作用于完整 token。项目采用这些可解释原则，但使用自己的轻量规则，没有复制官方 analyzer 的完整 Unicode、语言处理与停词配置。[CJK bigram 文档](https://www.elastic.co/docs/reference/text-analysis/analysis-cjk-bigram-tokenfilter)、[Stop token filter 文档](https://www.elastic.co/docs/reference/text-analysis/analysis-stop-tokenfilter)

这些规则仍是启发式：没有词典分词、同义词、实体识别或语义判断。二元相邻字符不等于中文语言学意义上的词；内容词有交集也不证明资料足以回答问题。新的召回边界由 `tests/test_retrieval_cache.py` 和原有未知主题测试约束，真实业务效果需单独标注评测。

## 2. BM25 保持什么，缓存什么

`retrieval.BM25Index` 为当前有效原文片段和有效已发布 Wiki 准备：

- 每个证据的词频与长度；标题按出现两次计权，正文按一次计权。
- 词项到候选编号的倒排表；查询只对匹配内容锚词的候选评分。
- `document`、`wiki`、`all` 三个语料视图各自的文档频率与平均长度，避免某类资料改变另一类单独检索的统计量。

排序仍为 BM25：`k1=1.5`、`b=0.75`，使用正值 IDF `log(1+(N-df+0.5)/(df+0.5))`，分数相同按证据 ID 排序。Apache Lucene 官方实现可核对这一 IDF 形式和长度归一化思想；其默认 `k1=1.2`，本项目的 1.5 与标题重复计权是本地基线，不是 Lucene 默认或经过调优的结论。[Lucene BM25Similarity 源码](https://github.com/apache/lucene/blob/main/lucene/core/src/java/org/apache/lucene/search/similarities/BM25Similarity.java)

Wiki 检索正文由标题、已引用的 claims 和 mode 重新构造。人工修订备注属于维护记录，不进入检索正文；历史页面与导出仍保留备注。纯空白原文窗口保留在持久化中保障 offset 完整，但不进入 BM25 候选。

## 3. 缓存为什么不用新连接的 data_version

项目每个存储操作新建 SQLite 连接。SQLite 明确规定 `PRAGMA data_version` 只能比较**同一连接**在不同时刻的结果；把新连接返回的整数当全局数据库版本不成立。因此这里没有用它判断缓存是否有效。[SQLite data_version 文档](https://www.sqlite.org/pragma.html#pragma_data_version)

`schema.py` 新增 `retrieval_state(id=1, epoch)`。`documents`、`chunks`、`wikis`、`wiki_sources` 的 INSERT、UPDATE、DELETE 都通过持久触发器递增 epoch；`runs` 没有触发器，所以记录一次查询不会让它刚建立的索引失效。epoch 是数据库变更代次，不是文档版本号或事务次数：一次导入多个片段可递增多次。

触发器和来源写入属于同一事务，回滚时一起回滚；新表、初始行和全部触发器在一次事务中安装。已有文档、Wiki、来源 ID 和运行历史不迁移、不重切；首次检索以新 epoch 加载既有资料。[SQLite CREATE TRIGGER 文档](https://www.sqlite.org/lang_createtrigger.html)

## 4. 一致性边界与失效流程

1. 每个 `KnowledgeStore` 拥有一个进程内 `SearchIndexCache`，使用 `RLock` 串行处理同一实例的冷构建。
2. 在一个显式只读事务中先读取 epoch。缓存命中时复用索引；未命中时，继续在**同一事务**读取原文、Wiki 与来源关系。
3. 构建完成后发布该快照的索引。索引评分在缓存锁和 SQLite 事务之外执行；返回结果使用独立副本，调用方修改列表不会污染后续查询。
4. 下一次查询重新读取 epoch，因此其他实例、其他进程通过这些表提交的更新也会触发重建。源更新、发布新版和依赖失效都由同一机制感知。

SQLite WAL 提供读快照：读事务开始后，其他连接的提交不会改变此事务已看到的数据库版本。这保证 epoch 和候选匹配，不会把旧代次配上新资料。[SQLite 隔离说明](https://www.sqlite.org/isolation.html)

这不是“查询结果永远等于返回瞬间的最新数据库”。在查询进行中提交更新时，正在执行的查询仍可能返回开始时的合法快照；下一次查询看到新代次。Agent 在输出最终引用前仍须重新读取证据，拒绝已经失效的版本。缓存不能代替最终引用校验。

缓存按完整当前语料重建，没有实现单文档增量倒排更新，也不在多进程间共享内存。每个进程会各自保留词频、倒排和文本；语料增长会增加内存、首次查询与更新后查询耗时。进程退出后缓存消失，数据库历史仍保留。

## 5. 数据库读取与观测接口

| 操作 | 当前 SELECT 次数 | 读取范围 |
| --- | ---: | --- |
| 冷检索 | 4 | epoch；原文片段与文档元数据 JOIN；有效发布 Wiki；批量 Wiki 来源 |
| 暖检索 | 1 | epoch；词频与候选使用进程内快照 |
| 文档列表 | 2 | 文档元数据；批量片段 ID，不读取正文 |
| 文档详情 | 2 | 一份文档；其全部片段，共享已读取的文档元数据 |
| 原文证据 | 1 | 片段与文档必要元数据 JOIN |

Wiki 候选同时检查发布状态、stale 和底层来源是否仍有效；存在新草稿时，仍可检索之前有效的已发布修订。批量 SELECT 不把每个 chunk 的整篇父文档正文反复搬入 Python。

`KnowledgeStore.cache_stats()` 返回 `ready`、`epoch`、`database_epoch`、`current`、`hits`、`misses`、`builds`、`items`、`terms`、`last_build_ms`。这些是实例级累计计数与最新构建信息；只有 database_epoch 来自数据库当前读快照。接口不返回查询、原文、配置、路径或密钥。它是观测值，不是任务完成或回答正确性的证明。

## 6. 可复现本地基准

在项目根目录用已存在的解释器执行：

```text
python scripts/benchmark_retrieval.py --output reports/retrieval-benchmark.json
```

脚本只生成临时合成资料，不读取用户知识库。固定 64 份资料、167,862 字符、256 个片段，4 个查询重复 3 轮，每条路径 12 个测量样本。测量包含 SELECT trace 与分词计数开销；排除建库、创建存储实例和暖缓存准备。p95 使用 nearest-rank，在 12 个样本中等于最大样本，不能当作稳定服务尾延迟。

旧路径复现 v2 的 N+1 整篇文档读取和逐查询全量重分词，使用同一修复后的查询锚词规则，以便隔离性能差异。冷路径每次用新存储实例；暖路径共享一次构建。三条路径逐查询核对证据、分数和顺序完全相同；这项检查不是答案质量评测。

Python 3.13.14 / SQLite 3.53.2 在本机的本轮实测已写入 [原始报告](../reports/retrieval-benchmark.json)：

| 路径 | 每查询 SELECT | 中位耗时 ms | p95 ms | 12 次内全量建词频次数 |
| --- | ---: | ---: | ---: | ---: |
| 旧式 N+1 + 重分词 | 257 | 63.155 | 68.654 | 12 |
| 新索引冷路径 | 4 | 60.581 | 70.679 | 12 |
| 新索引暖路径 | 1 | 3.183 | 4.177 | 0（测量前已构建 1 次） |

暖路径避免反复分词是主要收益。冷路径仍要读取和分词当前语料，本轮中位耗时接近旧路径，不能宣传冷启动显著加速。旧路径 12 次重复读取父文档正文合计 8,057,376 字符；新路径为 0，但仍读取必须检索的片段文本。报告提供逐样本数据、分词调用与字符数量，便于复核。这是单进程、小型合成语料的本机微基准，不是生产 QPS、并发容量或真实模型性能。

## 7. 为什么本轮不直接换为 FTS5

SQLite 官方说明 unicode61 将连续 token 字符视作一个 token，不等于中文词典分词；trigram 的全文查询对不足三个 Unicode 字符的片段不能命中。项目需要“和田”“异或”等二字查询，因此单独替换默认 tokenizer 不能证明解决问题。FTS5 的外部内容表还需要维护索引与来源同步。[SQLite FTS5 tokenizer 与外部内容文档](https://www.sqlite.org/fts5.html)

本轮保留可解释的词法规则与小语料缓存，先验证功能和读取成本。将来若改持久倒排、中文分词或稠密检索，应沿用版本和来源一致性测试，并独立评估召回、延迟与内存；不能把更换组件名称当作检索质量已经提高。

GitHub `main` 链接会随维护方变更；本文记录的是核验日期的设计事实，不是固定版本依赖。全部实现与基准均不需要下载包或访问模型。
